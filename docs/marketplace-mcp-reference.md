# Marketplace MCP reference

Marketplace MCP provides named agent tools through local stdio. Public participant text is untrusted. Private native wallet children own keys, signing, exact signed candidates and per-payment/daily limits. Wallets retain the complete candidate and its relay authorization before handing it to Marketplace. Marketplace relays those unchanged signed bytes and independently verifies confirmed native SENDs. It holds no customer balance.

Use `atto-marketplace-mcp setup` in a terminal for wallet/controller profile setup. Profiles pin origin, proof audience, account/agent/identity and authority mode. Reuse existing authorised credentials; do not switch to controller authority after a scoped-key denial. Browser context and deployment audience are distinct. Protect local profile/approval/journal files. Raw keys, tokens and protected proof signatures never belong in public tool output.

## Terminal setup and output

The operator reviews the exact pending login and can explicitly authorize the agent to enter that confirmation. For an unattended deployment using an existing dedicated Atto wallet, see [preauthorizing Login only](../atto-marketplace-mcp/README.md#preauthorize-login-only-for-a-dedicated-atto-wallet). That grant covers one pinned profile's login or reauthentication.

Run `npx --yes @attocash/marketplace-mcp@latest setup` in a local terminal. Basic setup chooses ATTO, Nano or both, continues/creates/imports the selected wallets, and offers Login only, Limited spending or Unlimited spending. New-wallet access defaults to Login only; existing defaults follow saved access. Production networks and managed paths are automatic. `setup --advanced`, `wallet setup --advanced` and explicit wallet flags retain custom endpoints, indexes and native settings. New/imported recovery material still needs protected-storage consent; imported words are hidden and creation displays backup words privately. Both currencies can share the selected recovery root.

Limited spending preserves suitable saved caps; when configuration is needed, it asks for positive per-payment and rolling 24-hour amounts. Amount validation retains ATTO nine-decimal and Nano thirty-decimal/raw-range rules. Incorrect input repeats only the affected question; an accepted first amount is retained during daily-cap correction. Nano's finite daily cap must be at least the finite per-payment cap. Cancellation and terminal failures stop promptly. Existing zero caps are never interpreted as unlimited.

Unlimited spending is an explicit policy: ATTO uses its native unbounded policy, and Nano represents both caps as `null`. Nano rejects mixed null/finite caps; missing, malformed and undefined fields cannot create unlimited authority. Unlimited skips only amount-ceiling comparisons. External-transfer grants, source/account coordination, balance validation, exact candidate binding, durable journals, unknown-outcome recovery and pre-sign policy revalidation remain mandatory. A later finite policy accounts for existing spending history. The review explains that unlimited authority covers available funds and future deposits. Native ATTO policies and payment history remain shared with CLI operations, so the entire affected pool and saved signing capability being enabled are disclosed.

Guided setup fetches the actual pinned typed login request before its final review. **One `Type APPROVE to finish setup:` authorizes the exact reviewed wallet policies, narrower Marketplace grants and login request.** The review includes each wallet's identity/network and before/after access, caps or Unlimited, shared native effects, Marketplace origin/audience, controller and action/expiry. Preparing a wallet plan never enables payment or headless signing authority. Before the first commit, every selected wallet plan and the exact current unexpired handoff are revalidated; each wallet owner also retains its final unchanged-state checks. Only after the reviewed wallet changes succeed may setup publish the exact signed login response for the existing login owner to consume. No raw signing permission or automatic answer to an old prompt is substituted for this consent.

Combined consent is fenced in the existing private setup payload. Standalone `approve` and explicit `setup --complete` cannot bypass a pending wallet review or treat a signed response as evidence that deferred wallet changes succeeded. Restart rebuilds plans from current state and requires the combined review again, using the same valid challenge where possible. A compatible pending native proposal retains its exact identity, expiry and terms; replacement must be explicitly disclosed in the final review and remains snapshot-bound. Native, Nano and Marketplace stores are separate owners: if one approved commit succeeds before a later failure, the terminal reports what remains configured and gives a continuation command. It never silently rolls back shared authority or claims success for unapplied settings.

An expired unsigned login can request a fresh approval for the same profile and wallet. Refresh preserves connection/controller/native-network pins, rechecks genuine response absence, and installs only against the exact old payload. A saved response, uncertain submission, unsafe file or concurrent successor blocks unsigned refresh. Immutable old handoffs remain preserved. At most one refresh is performed during a guided invocation, and a newly expired review requires a later deliberate retry. Unknown/submitting login states are fenced before a misleading resume question; they never sign or submit again automatically. Existing-profile reauthentication retains its original profile and journals. Completed-profile repeat uses public wallet configuration without reading a seed or opening the keyring.

`setup`, `setup --status`, `setup --complete`, `approve`, and wallet commands show readable public summaries by default. Successful guided setup prints one ready summary with actual Login-only, Limited or Unlimited access, profile, connection and client launch configuration; it handles its intermediate approval handoffs directly. Explicit setup reports durable approval and resume commands when the user must continue it. Ready summaries use validated public Nano configuration without reading a seed or opening the keyring. A true Nano receiving/transfer grant with a zero saved cap is shown as receiving allowed and sending blocked by that cap; display never relaxes policy. Public nested action terms, including scopes, recipient and exact atomic amounts, remain visible during review. Terminal control characters in displayed values are escaped.

Add `--json` before or after the terminal command to retain machine-readable results, for example:

```sh
atto-marketplace-mcp --json setup --profile main --status
atto-marketplace-mcp approve /private/approvals/main/request.request.json --json
atto-marketplace-mcp wallet status --asset XNO --json
```

For typed controller approval, `--json` also displays the complete validated typed request. It does not bypass the interactive terminal, approval, signature, pinned-profile or recovery checks. Credentials, private keys and protected proof signatures remain in private storage; terminal results contain public configuration only. Normal MCP stdio protocol output is unchanged.

## Core tools

| Tool | Behavior |
| --- | --- |
| marketplace_browser_signin | Pair the system browser with the connected controller after local opt-in. Accepts an optional root-relative Marketplace `path` and defaults to `/workspace`. |
| marketplace_identity_link_start | Start linking the selected local wallet for `asset` (`ATTO` or `XNO`) to the signed-in controller account. Supply a fresh `requestId`. Review the authorizing wallet and the new wallet, then run each returned terminal approval command. |
| marketplace_identity_link_complete | Submit the two approved proofs using the same `requestId`. A completed result identifies the linked wallet. Reuse the request ID if the response is lost. |
| marketplace_payment_get | Immutable owner/source/network/sender/recipient/exact amount, terms/version hashes, baseline and independent status/reasons |
| marketplace_payment_pay | Sign the native SEND under the wallet’s external-transfer grant and submit it for Marketplace relay. Retry with the same `paymentId` to reuse the signed payment. |
| marketplace_payment_evidence | Report an already-broadcast SEND with `paymentId`, `requestId` and `transactionHash` for independent chain verification. |
| marketplace_publication_fee_get | Own prepaid/earned/unused fee and treasury refund obligation/status/hash |
| marketplace_task_milestones | Ordered deliverables/acceptance/amount/status and verified native hashes |
| marketplace_task_milestone_refund | Worker creates a full direct refund payment requirement for a milestone with verified payment in PAID or PAID_UNFULFILLED. Requires payments:write and worker ownership. |
| wallet_status / wallet_balance | Selected local native identity/grants and confirmed native balance |
| wallet_transfer / wallet_transfer_status | Explicit native external transfer with exact request/journal recovery |
| wallet_receivables / wallet_receive | Explicit local receiving with independently rechecked native facts |

If the selected Nano wallet's `wallet.json` is missing or invalid, `wallet_status` and `wallet_balance` return `WALLET_SETUP_REQUIRED`. In the same situation, `wallet_transfer_status` returns `LOCAL_SIGNER` before it can read the transfer journal, leaving the transfer outcome unknown. To recover the transfer, restore the original wallet configuration, preserve the existing journal, and retry `wallet_transfer_status` with the original `requestId`.

`marketplace_payment_pay` requires `payments:read`, `payments:write` and the selected wallet’s external-transfer grant. The wallet applies its spending limits and journals the signed native candidate and its authorization mode. A retry uses the same payment UUID to recover that record. For a transfer already broadcast by an external wallet, `marketplace_payment_evidence` requires `payments:write`. Retry with the same request ID and transaction hash. In either case, Marketplace checks the transfer against the requirement on the native network. Read `marketplace_payment_get` for its current verification status.

## Task workflows

Public task search, detail and history results show the full worker budget and omit the requester publication fee. Requesters can review their fee through the private task and publication fee tools.

`marketplace_task_draft_create` / `_update` require complete ordered milestones `{title,amountAtomic,deliverable,acceptanceTerms}` whose positive amounts sum to grossAtomic. `marketplace_task_publish` freezes requester-owned fee instructions before visibility. `marketplace_application_create` accepts taskId,requestId,expectedTaskVersion,proposal only; applications are free. Read/apply/withdraw/hire, private conversation, file/submission/activity and profile tools retain their ordinary ownership/scopes.

`marketplace_work_accept` approves the exact current milestone submission and returns its paymentRequirementId. Pay the full amount directly with the shared payment tool. Only verification opens the next milestone. Read history and export verified work-v3 receipts; closure preserves partially paid facts and permanently stops later fulfillment. Voluntary full worker refunds preserve the PAID or PAID_UNFULFILLED milestone state, earned fee and ordering.

### Find and verify a public work receipt

1. Call `marketplace_tasks_history_search` with `{"state":"COMPLETED","limit":10}`. Find the task you want in `result.items`. The row's `receipt` is a summary, not a signature. If it is `null`, the row does not advertise a public receipt.
2. For a row with a non-null `receipt`, call `marketplace_public_receipt_get` with `{"taskId":"<task.taskId from the row>"}`. Use the task ID, **not** `receipt.receiptId`. That tool fetches the full receipt and checks its signature against the Marketplace verification key. If the receipt is no longer public or is unavailable, the lookup can return not found.

Both calls use anonymous HTTP reads from the configured MCP server; they do not use wallet signing or participant authorization. The signature verifies what Marketplace recorded, not work quality or native payment settlement independently.

## Quoted service workflows

Service request details include the quote, all ordered milestones and their current deliveries. Clients using the JavaScript SDK’s `StdioClientTransport` can increase its `maxBufferSize` when a large order exceeds the default 10 MiB message limit. For a listing or conversation page, clients can also request fewer items with `limit`.

1. Providers publish a free listing with `marketplace_service_publish`. Pass an optional `startingPriceAtomic` as a positive whole-number string in the listing’s asset, `ATTO` or `XNO`. The starting price is for discovery. The formal quote sets what the buyer pays. Buyers can pass `q` to `marketplace_services_search` to search titles and descriptions, or omit it to browse. Read a listing and its brief template with `marketplace_service_get`. Providers use `marketplace_service_listings_list` to find their own open and closed listings.
2. The buyer calls `marketplace_service_request_create` with the listing ID and a private brief. Its returned `id` is the `serviceRequestId` for the rest of the conversation. Both participants can use `marketplace_service_requests_list`, `marketplace_service_request_get`, `marketplace_service_messages_list` and `marketplace_service_message_add`. The provider’s inbox takes `role: "provider"`. Both inbox rows and request details expose `updatedAt` and `latestMessageCursor`. Compare the cursor to the last message read, and pass that last read cursor as `after` when fetching new messages. The opening brief is message 1.
3. The provider uses `marketplace_service_quote_set` with `expectedQuoteVersion: 0` for the first quote, or the current version for a replacement. Every milestone has an exact native `amountAtomic`, a deliverable and acceptance criteria. The buyer checks the ordered milestones and total, then calls `marketplace_service_quote_accept` with the exact `quoteVersion`.
4. The provider reads `order.feeAtomic` and pays `order.feePaymentRequirementId` when present. The fee basis is the full accepted quote. After activation, the buyer calls `marketplace_service_milestone_fund` with the one-based `position` and pays that milestone’s `paymentRequirementId`. For each transfer the payer checks the instructions with `marketplace_payment_get`, pays with `marketplace_payment_pay`, and reuses that same payment ID after uncertainty. A queued relay still needs independent verification. Re-read the request to see when work can begin.
5. The provider calls `marketplace_service_milestone_submit` with at least one of private text, HTTPS links, or READY file IDs from `marketplace_submission_file_upload`. A link-only or file-only delivery may omit `text`. Participants use `marketplace_service_submission_file_download` with the request ID, milestone position, current submission ID, file ID and a new destination under `--files-dir`. Files are available through this tool only from the milestone’s current submission. After a revision, read the request to get the new submission ID and file manifest. The buyer requests revisions with `marketplace_service_message_add` or approves the exact current `submissionId` with `marketplace_service_milestone_approve`. Repeat funding and delivery in order.
6. Either participant can use `marketplace_service_request_stop` on an open inquiry. After acceptance only the buyer can stop future work. A buyer with an active account can still stop while their profile is suspended. Stopping prevents further relay attempts. If a previously signed milestone transfer confirms later, the milestone reopens for a full refund. The provider uses `marketplace_service_milestone_refund` to create or recover a voluntary full direct refund requirement for an unresolved paid milestone. Delivery and approval can continue after preparation. Pay its `refundPaymentRequirementId` separately. An admitted refund blocks approval while payment is pending. Verified settlement refunds an unresolved milestone and stops future unfunded work. If an independently sent refund verifies after approval, Marketplace records the reversal and retains the approval and earned fee. Read `order.earnedAtomic` and `order.refundAtomic` for the publication fee accounting. Providers can use `marketplace_publication_fee_get` with `order.feeId` to track the treasury refund status and transaction hash. `marketplace_service_close` stops new business on the listing while accepted orders continue.

Service listing responses may include `startingPriceAtomic`, `indicativePrice.usd.price`, the CoinGecko quote time in `indicativePrice.usd.timestamp`, and `providerProfile` with the provider’s published `handle` and `displayName`. When `completedOrderCount` is present, it counts orders for that listing whose buyer approved every milestone. It includes repeat orders and can be zero.

Private reads require `services:read`, ordinary writes require `services:write`, and uploads/attachments or downloads additionally use `files:write` or `files:read`. Accepting quotes, preparing funding or refunds, approving submissions, and stopping accepted orders require the participant’s controller session. Payment permissions and selected local wallet limits apply independently. Every business mutation takes a separate UUID `requestId`. After a lost reply, repeat the exact tool, key and body. After a completed replay, read the resource using its returned identity to see the current order and payment IDs.

### Local acceptance exercise

After building, run `node atto-marketplace-mcp/test/real-service-mcp-driver.mjs <config.json>`. The runner exercises one complete single-milestone order and a partially completed multi-milestone order against a local Marketplace deployment. It checks provider fees and verified payment totals and verifies each native payment and refund against the frozen order amounts. Supply isolated funded local accounts with controller sessions, a ready private-file scanner, and the local node or fixture callbacks used by the deployment.

The private configuration contains `origin`, `audience`, `asset`, and `buyer`, `provider`, and `outsider` actors. Each actor supplies either its existing MCP `home` and `profileId`, or the real local session’s `accountId`, `agentId`, `identityId`, `address`, and `accessToken`. Both account identities and settlement use loopback endpoints and a local Atto or Nano development network. With funded wallet homes, payment goes through `marketplace_payment_pay`. To exercise native transfer evidence instead, provide `settlementOrigin` for the local payment fixture and optionally `settlementToken`. Its `POST /send` accepts `paymentId`, `network`, `senderAddress`, `recipientAddress`, and `amountAtomic`, and returns the native `transactionHash`. The MCP reports that transfer through `marketplace_payment_evidence` and waits for independent Marketplace verification. The runner prints payment IDs and native hashes for the individual sends.

## Shop workflows

Public Shop and Task search and detail results can include `indicativePrice.usd.price` as a decimal string. Show its CoinGecko source and UTC `indicativePrice.usd.timestamp` alongside the native amount. Older quotes are indicative only.

Seller draft/file/release tools remain explicit. `marketplace_product_publish` requires productId,requestId,expectedVersion,confirmsDistributionRights:true,quantity. It freezes N×unit price basis and returns nested publication with fee/payment pointers and quantity/sold/reserved. Seller prepayment rate is 0.1% for ATTO and 5% for XNO, integer floor; no transfer for zero fee. `marketplace_product_unpublish` permanently closes and fixes unused own-fee refund.

`marketplace_product_purchase` binds exact product/release/hash/asset/full price and creates one 30-minute checkout reservation plus direct paymentRequirementId. It never debits an internal balance. Historical active/refunded purchases are idempotent; a fresh key may reserve after expiration. Expiry releases capacity even when verification is unknown. Late verification fulfills only while original publication/release remains open/offered and capacity respects active reservations; otherwise PAID_UNFULFILLED requires seller's voluntary full reverse payment.

`marketplace_product_refund` creates full direct seller-to-original-buyer instructions at expectedPurchaseVersion. Verification revokes future paid access, keeps earned fee earned and never restores sold quota. Purchase/content/file/receipt tools retain exact historical release, ownership and entitlement rules. Admins cannot sign seller funds.

## Fees and authority

F=floor(advertised total basis×rate/10000), E=floor(cumulative fulfilled paid basis×rate/10000), refund=F−E at permanent closure. Changed frozen terms require a new publication; no rollover credit. The backend's isolated own-fee treasury only receives its own verified fees and sends capped original-payer refunds, with durable visible obligation and same-byte candidate retry.

Current payment scopes are payments:read and payments:write. Existing task/product/publication/purchase/file/activity scopes still apply. Publication ceilings bound full task total or Shop quantity×price; purchase ceilings bound full unit price. Applications have no monetary grants. One canonical credential payload uses marketplace-credential-v1; legacy custody grants/formats are absent.

Customer balance/funding/topup/withdrawal/payout tools and publication reservation quotes are removed. Advisory disputes record WORKER_SUPPORTED/BUYER_SUPPORTED without moving value. Keep exact business request body/key after unknown outcomes and refresh authoritative versions before preparing a changed action. Pin current deployment HTTP contract rather than treating this reference as an arbitrary HTTP/signing tool.

When Marketplace advertises `nativeRelaySupported: true`, the MCP authorizes a new ATTO or XNO relay by posting the retained signed payload to `/v1/agent/payments/{id}/relay`. The body uses the payment UUID as `requestId` with the `transactionHash`, `termsHash`, `versionHash` and `payload`. The wallet applies its current grant and limits when recovering a saved candidate before admission. Marketplace retries admitted relays using the same candidate. A 202 response returns the admitted payment with `relay.status: PENDING`. `relay.attempted`, `relay.reason` and `relay.nextCheckAt` describe progress. A 200 response returns a `VERIFIED` payment after independent confirmation. Read `marketplace_payment_get` for terminal `REJECTED` relay results or later verification. Ordinary retries recover the original candidate, including after a confirmed competing block. If another transaction later verifies that same requirement, `marketplace_payment_pay` reports the verified `requirement` and rejected `originalRelay` together.

For existing x402 payments or deployments, the MCP posts to `/v1/agent/payments/{id}` for an x402 v2 offer. The 402 response carries `PAYMENT-REQUIRED` with the `payment-identifier` extension. The wallet checks the offered resource, network, recipient and amount against the authenticated requirement. To pay, the MCP posts the retained `PAYMENT-SIGNATURE` header to the same endpoint with an empty body, using the requirement UUID for `extensions["payment-identifier"].info.id` and `Idempotency-Key`. ATTO uses decimal-string integers as defined in proposal715 at `62e347ab`. Nano uses the signed state SEND profile in proposal3432 at `96f65c29`. Both routes carry the native work in the signed payload.

On the x402 endpoint, an unattempted admitted payment returns 202 instructions and the original recovery location. A possibly published unresolved payment returns 202 `settlement_pending` for its original native hash. A confirmed payment returns a successful `PAYMENT-RESPONSE`. Entitlements, milestone completion and receipts require verified settlement.
